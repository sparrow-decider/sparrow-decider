# Sparrow Decider: decision models from 47 MB down to a few KB

Working report. Every number here comes from a file in `bench/results/` or a run log; the tables
are regenerated by `bench/aggregate.py`. Local runs on one Apple M4 Pro core unless stated; not
board scores. Unofficial community project, not an AWS or Strands product.

## 1. Problem

Strands Decider answers three kinds of question about a state (yes/no `noul`, pick-one `choice`,
ordinal `score`) with a 2B-4B language model plus a pointer head. That needs a GPU, or seconds per
question on a CPU, and gigabytes of memory. Agents and robots make many small decisions where a
library-sized model inside the process would do: which tool, which skill, which recovery, how urgent.

Goal: the smallest and fastest models that keep the Strands Decider contract, down to
microcontrollers, with honest measurements of what is lost.

## 2. Family

| Tier | Architecture | Init weights | Runtime |
|---|---|---|---|
| pico | one MLP per question on raw sensor features, compiled from a spec | none (distilled from a full decider) | generated C header |
| nano | static embeddings, pruned 8k vocab, 128-d, key-value number pooling, MLP | potion-base-8M (PCA-reduced) | C (SPB1 blob) and numpy |
| micro | static embeddings, full 29.5k vocab, 256-d, MLP | potion-base-8M | C and numpy |
| tiny | Ettin 32M bidirectional encoder + pointer head | Ettin encoder 32M | numpy |
| small | Ettin 68M bidirectional encoder + pointer head | Ettin encoder 68M | numpy |

## 3. Methods

### 3.1 Same contract, same prompt
States, questions and numbered options are rendered exactly as Strands Decider renders them, so
every tier reads what the big decider reads and returns the same answer shapes.

### 3.2 Encoder tiers (tiny, small)
A pointer head scores each option: `logit_k = <Wq LN(h_answer), Wk LN(h_opt_k)> / sqrt(d)`, where
`h_answer` is the mean of the encoder states over the `<answer>` tokens and `h_opt_k` the mean over
option k's span. One forward pass answers the question.

### 3.3 Static tiers (micro, nano)
No attention. The state, the question (plus a learned kind vector) and every option are
mean-pooled from a static embedding table, L2-normalised, and an MLP scores each option from
`[o, s*o, q*o, s*q*o, o - mean(o), (s - mean(o))*o]`. The set-contrast terms let the model compare
options with each other.

### 3.4 Key-value number pooling (nano)
Mean-pooled embeddings lose which number belongs to which key: "battery: 6%" and
"obstacle_m: 6" look alike. nano parses `key: number` and `key=number` pairs from the state and
builds, per pair, `emb(key) * tanh(G f(value))`, where f is four fixed numeric features and G is
learned. The MLP gets the mean of the pair vectors and, per option, an attention-weighted mix of
pairs keyed by the similarity between the option and the label at the start of each pair's line,
which binds "zone_b" to its own value. Four more feature blocks, ~1k extra parameters.

### 3.5 Distillation
A Strands Decider 4B checkpoint labelled the general training mix with its calibrated option
distribution. Targets are 50% teacher and 50% gold. A transfer set of re-paired states and questions
is labelled by the teacher alone.

### 3.6 Robot data
`training/gen_robot.py` generates six robot families (skill routing, sensor-driven action,
yes/no checks, recovery, urgency, compare) with randomised robots, field names, units, thresholds
and wording, and rule-derived gold labels.

### 3.7 Compression
Vocabulary pruning keeps the most frequent pieces plus every single-character piece, so any word
still tokenizes; models train on the pruned tokenization so training and runtime agree. Embeddings
are PCA-reduced for nano. All matrices are int8 with a per-row scale.

### 3.8 sparrow-pico: compiling a decision
For a fixed robot, the questions and the sensor schema are known when the firmware is built. A
spec lists the features (number ranges, flags, enums), optional plain-language rules, and the
questions. The compiler samples states, renders them as text, has a full decider answer every
question, and trains one small ReLU MLP per question on the raw feature vector. Output: a C
header with no dependencies.

### 3.9 Runtimes
- numpy (Python): pure-Python WordPiece and byte-level BPE, numpy encoder (matches torch to 3e-5).
- C99 (`c/sparrow`): no malloc, model blob read in place from flash, WordPiece by binary search
  over a sorted piece table, int8 weights. Matches the numpy runtime to 2e-6 in probability.

## 4. Benchmarks

- **JevBench public** (231 tasks): general decision quality, local v1.5 proxy scoring.
- **RobotBench v0** (55 hand-written robot decisions, `bench/robot`): written separately from the
  robot generator, with different robots, wording and thresholds, to measure transfer.
- **Pico rules check**: for compiled pico models, accuracy against the spec's own rules applied
  exactly, next to the teacher's accuracy against the same rules.
- **Runtime**: file size, peak memory, latency per question (numpy and C), C-vs-numpy parity.

### 6.2 What we learned

1. **Domain data beats size.**
   - micro rose from 22 to 30 on RobotBench after robot data was added, and JevBench didn't drop
     (114 to 117).
   - The 47 MB encoder tier, which never saw robot data, scores 24.
2. **Key-value number pooling is what makes numbers usable.** Across seeds and vocabulary sizes:

   | Config | Without kv: RobotBench (nav) | With kv: RobotBench (nav) |
   |---|---|---|
   | 8k vocab, 128-d | 32 (5/10) | 38, 38 (9/10, 10/10) |
   | 16k vocab, 128-d | 33 (4/10) | 42, 38, 41 (9, 8, 9 of 10) |
   | full vocab, 256-d | 31 (3/10) | 35 (6/10) |

   - kv costs some general accuracy: JevBench is 114 without it and 107 or 113 with it at 8k; at
     16k it is 123 without and 97-107 with. MASSIVE moves by a few points either way.
3. **Vocabulary pruning is cheap.** 8k-16k pieces with PCA to 128-d keep robot accuracy, and the
   model shrinks from 7.6 MB to 1.4-2.4 MB. At 4k pieces with 64-d (0.37 MB) skill routing drops
   (7/15) while navigation holds (8/10).
4. **Robot accuracy and general accuracy trade off at this size.**
   - On MASSIVE, which no Sparrow model trained on, every tier is far below the 2B (0.35-0.67 vs
     0.86 on domain routing).
   - Bag-of-embeddings models cannot read word order, and 1-8 MB cannot hold the 2B's breadth.
5. **Compiling beats generalising on a microcontroller.**
   - When the questions and sensor schema are fixed, a 1,500-parameter MLP distilled from the 2B
     matches the 2B's own accuracy against the stated rules: 94.3% vs 94.2% on the action question,
     and 99.8% vs 99.0% on the charging question.
   - That is about 230x smaller than nano per question, and over a million times fewer parameters than the
     teacher.
   - A pico model is only as right as its teacher. The 2B misses about 6% of action cases under
     explicit rules.
6. **Yes/no judgement stays near chance** for every tier on JevBench's 74 noul tasks, as in v1.0.
7. **The C runtime matches the numpy runtime exactly.**
   - Probabilities agree to within 8e-6, and argmax agrees on 586/586 cases for every model tested.
   - With `-O3 -ffast-math` it is faster than numpy: 0.12 ms for nano, 0.22 ms for micro.
   - Optional int8 activations cut micro to 0.16 ms, with 582/586 argmax agreement.

### 6.3 Limits of this evaluation

- RobotBench has 55 items, so one item is 1.8 points; seed-to-seed spread is up to 4 items.
- RobotBench and the robot generator were written by the same author, from different templates.
  MASSIVE is the independent check, and it shows the gap.
- Microcontroller timings so far come from Espressif's QEMU, which does not model real timing.
  Real ESP32-S3 numbers are pending hardware.
- JevBench figures are local proxy scores on the public tasks, not leaderboard results.
